## Decisions made

- **L1 (8 Nov 2026): the "same Wi-Fi fallback" is local discovery.** For phones where Nearby does not work (no Google Play Services, risk R3), the host announces itself on the local network (mDNS through the system's `NsdManager`) and listens on a local port; the other phone finds it and connects over a plain socket. No internet and no Google services needed. Cannot be tested on the emulator without extra setup; real phones and a loopback test cover it.
- **L2 (8 Nov 2026): the local link comes in three kinds, all built, and the app chooses: Noise, then TLS 1.3, then a plain link.**
  - **Plain:** the same messages as every transport, with a signed handshake in which the host proves it holds the key named in the ticket (a challenge it signs with its existing signing key). Sniffers on the network see public keys, counters, sizes and timing, not content (CRYPTO.md section 10).
  - **TLS 1.3:** the platform's own TLS, each side with a self-made certificate checked against the member's known key (the ticket's host key for a joiner). No cryptography of our own.
  - **Noise:** a Noise handshake through a library, each side with its key. **A new third-party cryptography library: it must be vetted and pinned (version, licence, maintenance, vulnerability check) and approved by the owner before it is added (see Open questions).**
  - **Choice:** the strongest first (Noise, then TLS, then plain). If one does not connect within a few seconds, the app moves down to the next. The signed announcement of what a phone supports means a failed attempt can be told apart from an older app. The status line says which kind was used. **Known cost (owner accepted this choice over "never fall back"):** a hostile network that breaks the stronger handshakes pushes everyone to the plain link, where the metadata above is visible. Nothing else is lost.

- **L3 (8 Nov 2026): libraries must be MIT or Apache-2.0; the rule applies to the libraries we add directly, not to what they bring in.**
  - **Noise: `nl.sanderdijkhuis:noise-kotlin` 1.0.1 (MIT).** Only the Noise state machine; Curve25519, ChaCha20-Poly1305 and SHA-256 are supplied by us through its `Cryptography` interface, built on Tink and the platform, so no new cryptographic primitive enters the app. Checks before it is added (T6.9): the handshake pattern we need (XX) is supported; the standard Noise test vectors pass through our `Cryptography`; it is not audited (the README says so), so our own tests and the owner's approval of that risk are part of the task; the version is pinned in `gradle/libs.versions.toml` and the vulnerability check covers it. If it cannot do what L2 needs, the task stops and asks (the fallback would be TLS plus plain only, which changes L2).
  - **QR generation: Nayuki's QR Code generator (Java, MIT).** One file with no dependencies, copied into the repo with its licence header (it is not on Maven Central); its tests are ours.
  - **QR scanning: `io.github.g00fy2.quickie:quickie-bundled` 1.12.0 (MIT).** Built on CameraX (Apache-2.0) and ML Kit (Google's terms, bundled so no Play Services are needed, about 2.5 MB more per ABI). Bundled, not unbundled, because of risk R3.

- **L4 (8 Nov 2026): no QR scanner in this version; joining is by pasting the link or code.** Quickie's ML Kit adds INTERNET and ACCESS_NETWORK_STATE and Google's reporting components to the app, which breaks "no network permission, no analytics" (found when it was added, and removed again). The options were a ZXing-based scanner (open source, camera permission only), Quickie with its Google parts stripped, or none; the owner chose none. The QR code on the invite screen stays (a phone's camera app can read it, and a scanner can come later); no camera permission is requested. **This replaces the Quickie part of L3.**
- **J1 (8 Nov 2026): the host describes the group when the invite is opened.** Opening an invite connects to the host, which sends the group's name, the owner's name and the member count sealed with the ticket's key (so only a holder of the ticket can read it). If the host cannot be reached the screen says "A group", explains, and the person can still ask to join later.

- **L5 (8 Nov 2026): the app asks for the INTERNET permission now, and nothing else, guarded by a test.** Found in T6.7: Android refuses every socket, even to a phone on the same Wi-Fi, without it. It replaces the release checklist's "no network permission" (BUILD_PLAN, M5 hand back) and brings forward what M7 needs anyway. It is for syncing with the other members only: `NetworkUseGuardTest` fails the build if any code outside the sync module and the one discovery file opens a connection or uses an HTTP client, or if a library that reports to anyone (Firebase, analytics, ML Kit, Play services and the like) is a dependency. The store listing and privacy text must say so (M10).

- **L6 (8 Nov 2026): no Noise link; the local link comes in two kinds, TLS 1.3 and plain.** This revises L2 (and the Noise part of L3). T6.9 checked `noise-kotlin` as L3 required and found it cannot do what L2 needs: it implements only the NK and XN patterns, and accepts a static key received in a handshake only if it was given beforehand as trusted, so a person joining a group (who knows the host's signing key from the ticket, not its Noise key) could not connect. The owner chose to drop Noise rather than extend the library or use it for members only: TLS already hides who syncs with whom, authenticates both sides by their member keys and works for joins; no unaudited library is added. Noise can come later with a better library. The choice (T6.10) is now: TLS first, plain if TLS does not connect.

## Plan (tasks)

Proposed order. Each task ends with tests first, as in M5.

- **T6.2 Join handshake.** Pure protocol in `app/sync`: the joiner shows the ticket id and the host proves its key; the joiner sends a request sealed with the group key (name, phone, keys); the host checks the ticket (issued, unused, not expired) and puts the request in the join requests list; after approval the host sends the group's history. Tests on the fake network: wrong host key, expired, reused, forged and malformed tickets are all refused without saying why.
- **T6.3 Issued tickets that survive a restart (CRYPTO C4).** A Room table for issued and used tickets; the group key is not stored a second time in the clear (keep a hash or seal it). Test: issue, restart, still single use.
- **T6.4 Invite screen** (mockup 10): QR, share link, copy code, expiry, revoke. QR via a vetted library (to be named in the task; no network).
- **T6.5 Join flow** (mockups 09 and 09b): paste or scan, waiting for approval, history arrives, and the first-run recovery of a phrase trying key slots in order (CRYPTO clarification C8).
- **T6.6 Host side wiring:** requests reach the join requests screen; approve admits (M4) and starts the history sync.
- **T6.7 Local link without security:** framing over sockets, the local discovery of L1, the plain link with the signed handshake. Loopback tests.
- **T6.8 TLS link.** **T6.9 Noise link** (after the library is approved). **T6.10 Choosing between the three** per L2, with the status showing the kind.
- **T6.11 Nearby transport and its screen:** runs only when the person asks (DESIGN.md), wait 15 s; permissions explained before they are asked; Location may be needed for discovery (spike finding).
- **T6.12 App wiring and hand back:** a real `Transport` in the app container (Nearby plus local), the Sync screen "Nearby" button, the manual two-phone checklist (invite by QR, scan, approve, history arrives, an expense on each side converges, airplane mode with Wi-Fi only), simulation still passing, docs.

## Results

### T6.2 Join handshake
**T6.2 result (8 Nov 2026).** Pure protocol, no screens and no transport: `JoinCrypto` (`app/crypto`), `JoinMessages.kt` and `JoinProtocol.kt` (`app/sync`), `TicketRegistry.find`. Messages and proofs are in WIRE_FORMAT.md section 7 and CRYPTO.md section 7a. The joiner sends the ticket id (not the ticket); the host answers with a fresh nonce and its signature; the joiner checks it against the host key in the ticket and only then sends the request, sealed with the ticket's group key and signed with its own key; the host opens it, checks the signature, uses the ticket up and keeps the request. Every refusal looks the same. A later connection can ask "what became of my request?" with a signed proof. **Tests (JVM, 15 + 6):** a good ticket is kept as a request and used up once; expired, unknown and used tickets are refused alike; a peer that is not the host named in the ticket is never sent the request and the real ticket stays usable; a request copied to another connection is refused and does not burn the ticket; someone who knows the ticket id but not the group key cannot use the ticket up; a request naming a key its sender does not hold is refused and the ticket is kept; two joiners with one ticket at once: one is kept; a host that cannot keep a request says the same refusal; the status answers only the holder of the key; silent peers time out; garbage and another group's room get no answer; strict message decoding including 2,000 random inputs; each proof is bound to its purpose, ticket, group, host and nonce. **Mutations** (six) each fail a test: no joiner-signature check, ticket used up before the key proof, host proof not checked, ticket never used up, status proof not checked, wrong room answered; the nonce left out of the sealed request's context fails the crypto test but not the protocol test, because the joiner's signature also covers the nonce (two layers on purpose). **Not yet:** independent test vectors for these proofs (to add before hand back); the host's backend (T6.6) and persisting tickets (T6.3); the joiner-side expiry check is the caller's (T6.5).

### T6.3 Issued tickets that survive a restart
**T6.3 result (8 Nov 2026).** `TicketRegistry` now keeps its records in a `TicketRecords` store and reads the group key from the keyring (`GroupKeys`) when a ticket is looked up, so **the record holds no copy of the group key** (CRYPTO C4: "must not keep a second plain copy"); a ticket whose key is not on the phone is simply not valid. New: `find(ticketId)`, `revoke(ticketId)` (for the invite screen, T6.4). `TicketRecord` is id, host, group, epoch, expiry, hint and used. **Database version 4** (`issued_tickets`, deleted with the group, `MIGRATION_3_4`, schema `4.json`), `RoomTicketRecords` (marking a ticket used is one `UPDATE ... WHERE used = 0`, so two callers cannot both succeed), and `Invites` (data layer: one registry per group, host key = this phone's key for the group). **Tests:** (crypto, 8) an issued ticket is accepted once after a restart; a used one stays used after one and another restart; the record holds no key (checked by looking inside it); a missing key means no ticket and it works again when the key is back; a ticket with another host, key, epoch or expiry is not the issued one and none of that uses it up; expired tickets are refused and dropped when another is issued; revoking one leaves the other; eight threads racing to use one ticket: exactly one wins. (data, 3) a real group's ticket is single use across a restart and carries this phone's key; no key in the keyring, no ticket; a group that is not this phone's has no registry. **Emulator (data, 39 tests, 9 skipped restart phases): pass**, including a file database closed and reopened twice (still single use, the table has no key column) and a version 3 file migrated to 4 with its data. Six mutations (accept not marking used, find ignoring used, find ignoring the host, revoke doing nothing, markUsed ignoring a used ticket, expired records never dropped) each fail a test; the fifth needed the thread-race test, added. **Not yet:** nothing issues tickets from the app (T6.4); the registries are not yet reachable from `Sessions`/`AppContainer` (T6.4/T6.6 wire `Invites`).

### T6.7 Local link, plain
**T6.7 result (8 Nov 2026).** **Frames** (`Frames`): four-byte length then bytes, over 1 MiB refused both ways, a cut-off frame is an error. **Handshake** (WIRE_FORMAT section 8, CRYPTO section 7b, `LinkAuth`): both sides show they hold their keys over a transcript that binds the pair of phones, the room and a fresh nonce from each side; a replay and a passed-off answer both fail. **`LocalNode`:** one phone's way of being reached and of reaching others: one port for every group and key it uses, routing by the room and key called, announcing each through a `LocalDiscovery`, handing on a connection only after both proofs; `SocketLink` is the `Link`. **Finding phones:** `NsdLocalDiscovery` (the app, Android's own mDNS, `_owntally._tcp`, names made by `LocalNames` that say nothing about the group or person) and an in-memory one for tests. **INTERNET (L5):** added to the manifest with `NetworkUseGuardTest` (replacing the older, narrower check) and `ManifestRulesTest` now expects exactly that one permission. **Tests (JVM, real sockets on loopback):** crypto 2 and sync 15: frames in order, empty, the largest, one byte at a time, over-long, negative and cut off at every point; names; two phones find each other, prove their keys and exchange messages both ways including a 1 MiB frame; a close ends the other side; a whole sync runs over the link; a phone not found, a dead address and a server that never answers are all "unreachable" within seconds; an answerer that signs with the wrong key is refused; a caller that signs with the wrong key, with zeros, replays a recorded handshake, names another room or key, sends garbage or a frame over the limit gets no link; a silent connection does not block the next caller; one node serves several groups and keys apart; **a phone in the middle passing one conversation's answer to a caller as another's to get in as someone else gets nothing.** **Emulator (app 9):** discovery finds a registered name and not another key or room; two nodes find each other **through Android's service discovery** and exchange messages over real sockets. **Mutations** (11) each fail a test: no check of the answerer's proof, no check of the caller's proof, a constant answerer nonce, no limit on read frames, the peer taken from the key called, a transcript without the caller's side, any room accepted, a cut-off frame accepted; two sharpened by a new test (the middle phone; read timeouts so a missing limit fails instead of hanging). Guard: a socket in the UI module and a Firebase dependency both fail the build. **Not yet:** the app does not start a `LocalNode` (T6.12 wires it in the app container); two real phones on one Wi-Fi (the owner's check); phones on Wi-Fi that blocks device-to-device traffic (guest networks) cannot use this link, which the status will say in T6.12; TLS and Noise (T6.8, T6.9) and choosing between them (T6.10).

### T6.8 TLS link
**T6.8 result (8 Nov 2026).** **The link inside TLS 1.3** (WIRE_FORMAT section 8, CRYPTO section 7c): `LocalNode.transportFor(identity, security = TLS)` dials a phone's TLS port and answers on its own; the platform's TLS does the encryption, with self-made certificates (`TlsCertificates`) that carry the member's key and the member's signature over the certificate's key, checked against the key the caller meant to reach; only TLS 1.3, both sides authenticated. **Three things found on the way:** (1) **A weakness in signature checking, fixed everywhere.** A flaky test showed that the Ed25519 verifier accepts a signature of zeros from a key of small order for about a quarter of all messages. `WeakKeys` (the libsodium list) is now checked before every signature in the app: envelopes, join proofs, link proofs and TLS bindings; a test shows the raw verifier accepting some and ours none, for every check, with 300 random messages each. It could not have let anyone in as a real member, but a "member" with such a key would have been forgeable by anyone once an admin approved a join from it. (2) **A bug of mine from T6.7:** the handshake read through a buffered stream and the link then opened another, so a message sent in the same breath as the proof could be lost; a test sends the proof and three messages in one write, failed, and the stream is now handed on. (3) **Android's TLS differs from Java's in two ways** that only the emulator showed: it does not give the key manager the name the caller asked for (so choosing the certificate by that name, which works on a laptop, fails there: each (room, key) now has its own TLS port, which also needs no guessing), and it cannot look up a certificate extension whose OID has numbers over 64 bits (the extension now has the short private-use OID 2.999.1). **Tests (JVM, real sockets on loopback):** sync 10 TLS tests plus 7 on the certificate and 2 more on names: two phones talk inside TLS and each knows who the other is (including a 1 MiB frame and a whole sync); **on the wire a message is readable on the plain link and not inside TLS, nor who calls whom**; a server whose certificate carries another member's key, or an ordinary self-signed one, is refused; a caller with no certificate, an ordinary one, a forged claim, only TLS 1.2 or garbage gets no link; a message right after the handshake is not lost; one node keeps several groups' and keys' TLS links apart, and a caller sent to the wrong key's port is refused; the certificate is a proper X.509 that the JDK parses and whose signature it verifies, and a certificate whose binding covers another key, was made by another member, is missing or malformed is not accepted. **Emulator (app 10):** two nodes talk inside TLS 1.3 on the Android runtime, through Android's service discovery. **Mutations:** 9 each fail a test (binding signature not checked, self-signature not checked, any certificate trusted, TLS 1.2 allowed, a link handed to another peer or another identity's inbox, no check of the weak list at each of three sites, and others); ### T6.9 Noise link (dropped)
**T6.9 result (8 Nov 2026): not built, by decision L6.** The check that L3 asked for found the library lacks what L2 needs (see L6): only the NK and XN patterns, and a received static key must already be in a trusted set. Options put to the owner: drop Noise; use the library's NK between members only (joins stay on TLS or plain); add the XX pattern to a copy of the library. The owner chose to drop it. Nothing was added to the build. **For later, if Noise is wanted:** a library with the XX or IK pattern, independent test vectors for those patterns, and a way for a joiner to learn the host's Noise key (for example the ticket carrying it, which changes the ticket format the owner approved).

### T6.10 Choosing the link
**T6.10 result (8 Nov 2026).** `LocalNode.secureFirstTransportFor(identity)` (WIRE_FORMAT section 8): TLS first, the plain link if TLS does not connect within `tlsAttemptMs` (5 s); a phone that answers with the wrong key is a refusal and gets **no** plain attempt; both kinds arrive in one inbox; `LocalConfig.offerTls` lets a phone offer no TLS (an older app, or a platform without it).
