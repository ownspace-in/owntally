# M11 tasks: restoring from the recovery phrase

Parent: [BUILD_PLAN.md](../BUILD_PLAN.md), milestone M11. Rules: [DESIGN.md](../DESIGN.md) "Recovery", [CRYPTO.md](../CRYPTO.md) sections 2, 6 and 7, [PROTOCOL.md](../PROTOCOL.md), [WIRE_FORMAT.md](../WIRE_FORMAT.md). Tests first. Decision X1 (9 Nov 2026) put restore here.

Goal (BUILD_PLAN): enter the 12 words on a new phone and get the same identity back; for each group, a friend's invite brings the phone back in as the same member with no new approval, and the history syncs. Acceptance: a phone that was wiped and restored from the phrase rejoins every group it was in without an admin's approval and **ends with the same balances**; tests with a wrong phrase and with another person's phrase.

## What already exists (so it is not rebuilt)

- The seed and every group key pair come from the phrase and a numbered slot (`KeyDerivation.groupIdentity`); `IdentityRepository.completeFirstRun(phrase, name, phone)` stores a seed from any valid phrase (the M6 tests already restore a phone this way).
- `JoinGroup.findMySlot(ticket, maxSlots = 16)`: asks the invitation's host, one connection per slot in order, which slot's key is already a member (the host answers a status question only to the holder of that key). Tested in `JoinGroupTest`.
- The host side: `GroupJoinBackend.statusOf` answers `APPROVED` for a current member; `JoinRequests.receive` ignores someone who is already a member ("needs no approval", DESIGN.md).
- Words are checked by `Bip39.check` with a `PhraseProblem` that never holds the words.

Not built: the restore screens, the joining path that uses `findMySlot`, protection against reusing slots, and (found in planning, below) a way to read earlier epochs.

## Finding P1 (found 11 Nov 2026, before any code): a member who joins after a key change cannot read the group

An invitation carries the key of the epoch it was made in, and a key change (`MemberRemoved`, `KeyRotated`) seals only the **new** key, to the members of that moment. So nobody who arrives later holds the keys of the epochs before the one in their invitation. A probe (a group with an expense, then `rotateKey`, then a new member through the real invitation, approval and sync) gave: **0 expenses, 0 members, epoch 0, "waiting for key: epoch 1"**. The group's creating event is in epoch 1, so the whole state stays empty: the joiner cannot even see the group's name. The same holds for a restored phone: it can recover the keys sealed to its key (epochs in which it was a member), but never epoch 1, nor any epoch before it was admitted.

This is not new in M11: it affects every group that ever had a removal or a key change, and nothing in M1 to M10 tests it (`KeyCoverage` says an admitted member "gets the key with the history", which holds only for the current epoch). It has to be fixed for the M11 acceptance ("ends with the same balances") and it is a real defect for ordinary joins already.

## Decisions made (owner, 11 Nov 2026)

- **D1 = A, key chaining.** After every key change the previous key is handed to whoever holds the new one, so whoever holds the newest key can reach epoch 1. Short links; WIRE_FORMAT, PROTOCOL and CRYPTO updated; no migration (no release exists). (How it is done changed while building: see T11.1.)
- **D2 = the key of a group is derived from the group id, not from a counter.** The owner chose this over the 64-slot window. **How the builder reads it (to confirm in the pull request):** the HKDF derivation of `KeyDerivation.groupIdentity(seed, slot)` (CRYPTO.md section 2) stays exactly as it is, which keeps every test and the stored `key_slot` column; what changes is **which number is used**: no longer a counter but `slot = first 62 bits of SHA-256(label, group id [, generation])`. For a member the label is `"owntally/v1/slot/member"` and the generation is 0, 1, 2, ... (a person who left a group cannot be re-admitted under the same key, so rejoining needs the next generation); for a group's creator the label is `"owntally/v1/slot/creator"` and the input is the 8 random bytes of the group id (`GroupIds.create` already puts them first, and checks the creator's key against the other 8 bytes), so the creator's key is derived *before* the id exists and can be derived again from the id alone. Nothing is searched and nothing is remembered: on restore, an invitation names the group id, the phone computes the creator slot (valid only if `GroupIds.isCreatedBy` holds) and the member slots for generation 0, 1, ..., and asks the host about each in turn until one is a member (restored), or free (a new join), skipping removed or declined ones. Normal joins ask once. The 62-bit slot makes two groups getting the same key practically impossible (2^-62 for a pair) and needs no list of used slots; `reserveSlot` and the counter go away. The wider slot widens CRYPTO.md's `u32` slot to 62 bits (the number is written in decimal in the HKDF info text, so the derivation is unchanged for the slots the tests already use).

## Tasks

- **T11.1 Key chaining (D1). Done (11 Nov 2026).** **Built differently from the first plan, for a reason found while building:** the event that starts an epoch is encrypted under the *old* key, so a box inside it (the first plan) cannot be read by someone who holds only the new key. Instead the owner's phone writes a new event, `KeyLinked(epoch, previousKey)` (tag 17), **right after** every key change; it is written in the new epoch, so it is encrypted under the new key, and it holds the key of the epoch before. Whoever holds epoch *n*'s key reads the link of *n*, takes the key of *n - 1*, reads the link of *n - 1*, and so on to epoch 1. No new cryptography. **A second thing found while building:** replay holds the link back (it follows events a late member cannot yet read), so the key is taken from the opened event, not from replay's state; the safety is authenticated decryption (a key is stored only if it opens an entry of that epoch), so it does not matter who wrote the link. If the owner's phone stopped between the key change and the link it writes the missing one the next time it reads the group. WIRE_FORMAT.md (tag 17; unknown tags start at 18), PROTOCOL.md (the rules: owner only, the epoch the author was in, first one counts, `GroupState.keyLinks`) and CRYPTO.md section 6 ("Key chaining") updated first. **Tests:** `KeyLinkedTest` (7, the replay rules), the wire vectors (the independent Python encoder gained tag 17; `WireCodecTest` 21), `KeyChainingTest` (5: **the probe of finding P1 as a real test** now passes: a member admitted after a key change reads the whole history and gets the same balances; the chain across three key changes; the link is written in the new epoch; the owner repairs a missing link by itself and only once; a link with a wrong key is not taken and nothing breaks). **Mutations (4), all caught:** link not written, a key accepted without opening anything, the chain never adopted, the repair removed. All unit tests and lint pass.
- **T11.2 Slots from the group id (D2). Done (11 Nov 2026).** CRYPTO.md section 2 and DESIGN.md "Recovery" first; `KeySlots` in the crypto module (member slot from the group id and a generation; creator slot from the 8 random bytes of the id); `KeyDerivation` accepts 62-bit slots; `GroupIds.randomPart`; `GroupRepository.createGroup` derives the creator's key from the random part and builds the id from it; `JoinGroup` uses generation 0 for a first join (generations for a rejoin are T11.4). `IdentityRepository.reserveSlot` is now `internal` (a helper for the tests' made-up members) and the app keeps no counter. **Tests:** `KeySlotsTest` (7; the numbers equal an independent Python implementation, which also gained the 62-bit slot vectors; every slot is valid; a creator finds their key again from the id alone and another person's phrase does not; a member's key is not the creator's), `GroupRepositoryTest` (a phone restored from the same phrase derives the creator's key from the id alone; no counter is kept; a deleted group's key is not given to a new group), `JoinGroupTest` (a first join uses generation 0). Four old tests that asserted the counter ("slots 0 and 1", "a failed attempt uses up a slot", "a slot is never reused") were rewritten for the new rule. **A test flake found on the way (not an app fault):** `NearbySessionTest.aMemberNotFound...WhicheverPhoneHasTheLargerKey` failed about 1 run in 14 because it reused one pair of pretend phones for both cases, and the case where the *smaller*-key phone is lonely second finds the larger one's leftover mailbox in the pretend network; the keys used to be fixed so only one order ever ran. It now uses fresh phones for each case, picked by key order, so both orders always run. All unit tests and lint pass.

- **T11.4 Rejoining. Done (11 Nov 2026).** `JoinGroup.resolve`: from an invitation the phone asks the host about its candidate keys in turn, each with the proof of its own key (the host answers only the holder): the group's **creator key** first (only if the group id vouches for it, so a non-creator costs no connection), then **member generations 0, 1, 2, ...** (at most 32): *member* means a restored phone, so `JoinGroup.open` makes the group on the phone with that slot, keeps the invitation's key and starts the sync with the host, and answers `OpenResult.Restored` (no request, no approval); *nobody the host knows* means a new join under that key (a person who left comes back under the next generation, because generation 0 is a removed key and removed keys are skipped); a stranger's or another person's phrase finds nobody and joins as usual. `request()` asks again while the join is only opened (the host may have been away at the start) and can answer `RequestResult.Restored`. `findMySlot` and its M6 test are gone. The app container maps a key to its slot for a group by trying the derived candidates too (otherwise the connections of the search would have had no transport). The UI opens the group on `Restored` (pasted link, tapped link, and the request button). **Tests (`RestoreRejoinTest`, 6):** a restored member is recognised, rejoins with no request and the **balances equal the old phone's after a sync**; a restored creator is recognised by the key the group's id vouches for; someone who left comes back under generation 1 and a later restore finds generation 1; a phone never in the group joins as new under generation 0; another person's phrase is not recognised even when the real one is a member; with the host away the invitation opens under generation 0 and the restored member still gets in when the host is back. **Mutations (6) caught:** removed keys not skipped, a member not recognised, the creator key never tried, the creator check dropped, the request not looking again, the sync not started. **Not decided by a test, noted:** the invitation is not used up by a restored member (the host's status answer does not consume it); the host's person can cancel it on the invitations screen.
